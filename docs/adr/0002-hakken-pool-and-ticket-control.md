# ADR-0002: はっけん出題プールとチケット制御の簡素化

## Status

Accepted

## Context

はっけん機能の出題制御に3つの軸が混在していた:

1. **日次回数制限**（`daily_hakken_max` / `daily_hakken_usage`）: 1日あたりの新規はっけん回数を制限
2. **チケット残高**: 新規はっけん1回につき1枚消費
3. **静的プリセット語リスト**（`HAKKEN_WORDS`）: みつけるの出題プール

日次制限とチケットは制御の目的が重複しており（どちらも「遊びすぎ防止」）、保護者から見て理解しにくい。また ADR-0001 で「プリセット語は本番では持たない」と決定済みだが、`HAKKEN_WORDS` がコードに残っていた。

加えて、たんけんで既にずかんにある語を入力すると「もう ずかんに あるよ」でブロックされていたが、再発見（同じ語をなぞり直す）は子どもにとって楽しい行為であり、ブロックすべきではない。

## Decision

1. **日次回数制限を廃止**し、チケット残高のみで新規はっけんの可否を制御する
2. **HAKKEN_WORDS を廃止**し、みつけるの出題プールを `prepared` → `shared_cache` → 収集済み（review）に変更する
3. **たんけんの重複ブロックを廃止**し、ずかんにある語は再発見（チケット不消費）として書く画面へ通す

## Alternatives Considered

| 選択肢 | 利点 | 欠点 | 不採用の理由 |
|--------|------|------|------------|
| 日次制限 + チケット併用を維持 | 保護者が細かく制御できる | 制御軸が2つで混乱する。設定画面が複雑になる | チケット購入量で利用量は十分制御可能 |
| HAKKEN_WORDS をサーバーサイドの語彙 DB に移行 | 出題語の管理が柔軟に | プリセット語の運用コストが発生。shared_cache で十分 | ADR-0001 で「プリセット概念は本番では持たない」と決定済み |
| たんけんの重複を「再発見しますか？」確認付きで通す | ユーザーが意図的に再発見を選べる | 毎回の確認が遊びのテンポを損なう | 再発見はチケット不消費なので確認不要。子ども向けにシンプルさが重要 |

## Consequences

**良い面:**
- 制御の軸が1つ（チケット）に統一され、保護者の理解が容易になる
- 出題プールが shared_cache に基づく動的なものになり、ユーザーが増えるほど語彙が豊かになる
- 再発見が自然に遊びの一部になり、子どもが好きな語を何度でもなぞれる
- 日次制限関連のコード（マイグレーション、サービス、テスト）を削除でき、コードが簡素化される

**悪い面:**
- shared_cache が空の初期状態では、みつけるの出題語が prepared のみになる。サービス開始時にシード投入が必要
- チケットのみの制御は「1日中遊び続ける」を防げない。ただし保護者が端末を管理する前提
- HAKKEN_WORDS 削除により `/api/hakken/random` がサーバーサイドで shared_cache を参照する必要があり、API 構成が変わる
