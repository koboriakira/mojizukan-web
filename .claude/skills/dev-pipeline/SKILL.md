# dev-pipeline

Issue ベースの開発パイプライン。開発開始時のテスト設計と、PR 前のスコープ・受入検証を統合する。

## 入力

```
/dev-pipeline start <Issue番号>
/dev-pipeline finish <Issue番号>
```

---

## start: 開発キックオフ

Issue を読み、要件を抽出し、テストスケルトンを生成する。

### ステップ 1: Issue の取得

```bash
gh issue view <番号> --json body,title --jq '{title: .title, body: .body}'
```

### ステップ 1.5: グロッサリー・ADR 確認

Issue のタイトルと本文に含まれるドメイン用語を `docs/glossary.md` と照合する。
また `docs/adr/` の Accepted な ADR で関連するものがないか確認する。

- グロッサリーに定義済みの用語があれば、その定義を要件整理に活用する
- ADR で否定された選択肢が Issue に含まれていれば警告する
- 新しいドメイン概念が登場していれば、グロッサリーへの追加を提案する

### ステップ 2: 要件の抽出（フォーマット非依存）

Issue 本文から要件を抽出する。以下の優先順で探す:

1. `## 受入条件` セクション内の `- [ ]` 行
2. `## やること` / `## 変更内容` セクション内の箇条書き（`- ` で始まる行）
3. 上記がなければ、本文中の全箇条書き行を候補とする

ネストされた箇条書き（`  - `）はサブ要件として親に紐づける。

### ステップ 3: ユーザー確認

抽出した要件を番号付きリストで提示し、過不足がないか確認を求める。ユーザーが修正したらそれを採用する。

UI・画面遷移・アニメーションを含む要件がある場合:
- 各状態のUI遷移を確認: **正常完了** / **エラー時**（ボタン・入力の活性/非活性）/ **ローディング中** / **空状態**（データなし）
- 要件に上記が欠けていれば、ユーザーに補足確認する
- プロジェクトの CLAUDE.md のテスト方針を参照し、E2E テストの追加・更新が必要かを併せて提示する。

### ステップ 4: テストスケルトン生成

プロジェクトのテストフレームワーク（vitest/jest/pytest 等）と既存テストファイルの配置を検出し、スケルトンを生成する。

- `describe("Issue タイトル")` で囲む
- 各要件を `it("要件テキスト")` に変換（日本語のまま）
- 本体は `// TODO` で空にする（実装は CLAUDE.md の TDD サイクルが行う）
- How（実装方法）ではなく What（何が成り立つか）を書く

#### E2E テストの自動検討

`src/client/*.ts` への変更を含む要件がある場合、E2E テストスケルトンの生成を**自動で提案する**（ユーザーに「E2E 要る？」と聞かない）。

判定条件:
- 要件が画面遷移・条件分岐・状態管理の変更を含む
- 要件が UI テキスト・ボタン・フロー分岐を変更する
- 要件が複数画面にまたがる状態伝搬に影響する
- サーバー側の変更がユーザー観測可能な画面挙動を変える（レスポンス構造・リダイレクト先・エラーハンドリングの変更など）

生成方針:
- 新規テスト追加より既存テストへのステップ追加を優先する
- E2E テストを増やしすぎない原則は維持する（CLAUDE.md 参照）
- クライアント JS はテンプレートリテラル内のためユニットテストでフロー検証できない旨を明記する

### ステップ 5: 出力

```
## dev-pipeline start 完了: Issue #XX

### グロッサリー確認
- 関連用語: <用語> — <定義>
- 関連 ADR: <ADR番号> — <タイトル>（Accepted）

### テストスケルトン
- `<ファイルパス>` に N 件のテストを生成

### 要件 → テスト対応表
| # | 要件 | テスト名 |
|---|------|---------|
| 1 | ... | it("...") |
```

---

## finish: PR 前検証

スコープ逸脱チェック（余計なものがないか）と受入条件チェック（必要なものがあるか）を実行する。

### ステップ 1: 要件の再抽出

start と同じロジックで Issue から要件を取得する。

### ステップ 2: diff の取得

```bash
git diff main --stat
git diff main --name-only
```

### ステップ 3: スコープチェック（負の検証）

変更ファイルを Issue の要件と照合する:

- **ファイルスコープ**: 要件に関係ないファイル変更を警告
- **機能スコープ**: `## スコープ外` に明記された機能の実装を検出
- **リファクタリングスコープ**: Issue 無関係なリファクタリング混入を検出
- 小さな修正（typo、import 整理）は逸脱としない

### ステップ 4: 受入条件チェック（正の検証）

各要件について:

- **テスト存在**: 対応するテストが存在し `npm test` で通過するか
- **コード変更**: diff に対応する実装が含まれるか
- **手動確認**: CSS・UI・アニメーション等、自動検証できない項目を明示

### ステップ 4.5: CI ステータス確認

PR が存在する場合、CI の状態を確認する:

```bash
gh pr checks <PR番号>
```

- CI がすべてグリーン → マージ可能として報告
- CI が失敗 → 失敗内容を報告し、マージを保留
- CI が未実行 → push 済みか確認し、実行待ちであればその旨を報告

PR 本文に `Closes #<Issue番号>` （または `Fixes #` / `Resolves #`）が含まれているか確認する。欠けていれば警告し、追加を提案する。

### ステップ 5: 出力

```
## dev-pipeline finish 結果: Issue #XX

### スコープチェック
- src/routes/hakken.ts — OpenAI → Workers AI 移行 ✅
- src/lib/ai.ts — AI クライアント新規作成 ✅
- ⚠️ src/client/app.ts — ホーム画面のテキスト変更（Issue スコープ外の可能性）

### 受入条件チェック
| # | 要件 | テスト | 実装 | 判定 |
|---|------|--------|------|------|
| 1 | ... | ✅ | ✅ | ✅ |
| 2 | ... | ❌ | ✅ | ⚠️ |

### カバレッジ: N/M (XX%)
### 判定: ✅ 通過 / ⚠️ 条件付き通過 / ❌ 未達
```

---

## 原則

- **フォーマット非依存**: Issue の書式が `- [ ]` でも箇条書きでも動く
- **ブロックではなく警告**: 検証結果は判断材料として提示し、進行を強制停止しない
- **TDD サイクルには踏み込まない**: 実装中の Red-Green-Refactor は CLAUDE.md のサイクルに委ねる
